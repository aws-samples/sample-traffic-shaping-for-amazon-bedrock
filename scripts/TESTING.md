# Testing Capabilities

This document describes the testing tiers in this repo — when to use each one, how to
run it, and what the output tells you. Read this before starting any testing work in a
new session.

All tooling here is either offline (no AWS) or driven directly against the deployed
stack via the AWS SDK (boto3) and the `make` targets. There is no external load-testing
harness — sustained and overload traffic is generated by the in-repo Python scripts
below.

---

## Testing Tiers at a Glance

| Tier | Tool | Requires AWS? | Speed | When to use |
|------|------|:---:|------|-------------|
| 1 — Unit / expression | `pytest tests/` | No | Seconds | Before every deploy — catches DynamoDB expression bugs and units-contract regressions that only surface at runtime |
| 2 — Dispatch simulation | `scripts/test_queue_processor_sim.py` | No | Seconds | When changing `queue_processor.py` dispatch logic — proves correctness before touching Lambda |
| 2b — Admission simulation | `scripts/test_budget_manager_sim.py` | No | Seconds | When changing `budget_manager.py` / `put_allocation` admission logic, or tuning a quota config — predicts the admit/enqueue split before a live load test |
| 3 — Algorithm comparison | `scripts/test_dispatch_algorithm_sim.py` | No | Seconds | When evaluating algorithm changes — side-by-side CURRENT vs PROPOSED vs TOKEN-AWARE |
| 4 — Live integration & comparison arms | `make test`, `make test-budget-manager`, `make test-direct-*` | Yes | Minutes | After deploy — confirms end-to-end behaviour and generates apples-to-apples shaper-vs-direct comparison arms |
| 5 — Sustained load & soak | `make soak-test` (any duration via `--duration-hours`), `make test-multi-model` | Yes | Minutes–hours | Proving behaviour under sustained quota overload and multi-model contention; long-horizon stability |
| 6 — Conflict attribution & outcome reconciliation | `make analyze-conflicts`, `scripts/reconcile_outcomes.py` | Yes | ~30s | Post-run — attributing TransactionConflict sheds to specific gate items and computing honest terminal-outcome success rates |

## Tier 1 — Unit Tests (`pytest`)

**Files:** `tests/test_admission_expressions.py`, `tests/test_create_model_config.py`,
`tests/test_flat_tpm_estimate.py`, `tests/test_runtime_reconciliation.py`

Validates DynamoDB `TransactWriteItems` condition expressions against a local moto
in-memory DynamoDB, plus config generation, the flat TPM estimate, and the runtime
consumption-reconciliation units contract. Catches `ValidationException` errors (illegal
expression syntax) that `py_compile` cannot detect, and pins the burndown-weighted token
accounting.

```bash
python -m pytest tests/ -q
```

Run this before every `make deploy`. A failing expression will cause 100% admission
failures in production — this test catches it for free.

## Tier 2 — Queue Processor Dispatch Simulation

**File:** `scripts/test_queue_processor_sim.py`  
**Library:** `scripts/sim/` (`config.py`, `core.py`, `__init__.py`)

Simulates the `queue_processor.py` dispatch loop using a fake wall clock — no AWS
dependencies, no deployed stack required. Proves that the TOKEN-AWARE algorithm
produces zero RPM and TPM window violations across production-scale workloads, while
the legacy CURRENT algorithm does not.

### When to run

- Before or after modifying `queue_processor.py` dispatch logic
- When tuning `SHORT_WINDOW_SEC`, `tpm_2s_cap`, or `rpm_2s_cap` constants
- To validate that a new quota profile respects both RPM and TPM gates

### Usage

```bash
# Default: smoke test + all three production workloads (rpm-push, tpm-push, mixed-spike)
python3 scripts/test_queue_processor_sim.py

# Skip the smoke profile, run production workloads only
python3 scripts/test_queue_processor_sim.py --no-smoke

# Single workload
python3 scripts/test_queue_processor_sim.py --workload tpm-push

# Against a named quota profile (mirrors real DynamoDB configs)
python3 scripts/test_queue_processor_sim.py --profile nova-lite
python3 scripts/test_queue_processor_sim.py --profile claude-sonnet

# Custom quota (overrides profile)
python3 scripts/test_queue_processor_sim.py --rpm 1500 --tpm 3000000

# Per-dispatch trace (verbose — one line per dispatch event)
python3 scripts/test_queue_processor_sim.py --workload mixed-spike --verbose

# Tune the burst/queue capacity split fractions
python3 scripts/test_queue_processor_sim.py --queue-fraction 0.40 --burst-fraction 0.55
```

### Available profiles

| Profile | RPM | TPM | Notes |
|---------|-----|-----|-------|
| `smoke` | 100 | 100k | Fast end-to-end sanity check |
| `dev` | 500 | 1M | Light dev quota |
| `prod` | 2000 | 4M | Typical production |
| `nova-lite` | 2000 | 8M | Nova 2 Lite confirmed quota (us-east-1) |
| `nova-pro` | 1000 | 6M | Nova Pro estimate |
| `claude-haiku` | 4000 | 8M | Claude Haiku |
| `claude-sonnet` | 2000 | 6M | Sonnet 4.6 confirmed quota (us-east-1) |
| `claude-opus` | 500 | 30M | Opus 4.7 runtime |
| `prod-high` | 5000 | 10M | High-throughput enterprise |

### Available workloads

| Workload | Character | Binding constraint |
|----------|-----------|-------------------|
| `rpm-push` | Many small requests (150–1k input tokens) | RPM |
| `tpm-push` | Many large requests (20k–100k input tokens) | TPM |
| `mixed-spike` | Medium base + 15% oversized spike items | TPM (spike items exceed the 2s window) |

### What to look for in output

Each scenario prints per-algorithm assertion results:
- **RPM window violations** — dispatches that exceeded the per-second RPM cap within the
  2s rolling window. Should be 0 for TOKEN-AWARE.
- **TPM window violations** — dispatches that exceeded the per-second TPM cap within the
  2s rolling window. Should be 0 for TOKEN-AWARE; CURRENT/PROPOSED will show violations
  on tpm-push and mixed-spike.
- **Drain efficiency** — fraction of items dispatched vs queued. TOKEN-AWARE trades a
  small efficiency cost for zero violations.

## Tier 2b — Budget Manager Admission Simulation

**File:** `scripts/test_budget_manager_sim.py`
**Library:** `scripts/sim/` (same shared library as Tier 2)

Simulates the `budget_manager.py` **admission** path using a fake wall clock — no AWS
dependencies, no deployed stack. Where Tier 2 models the single-threaded queue *drain*,
this models the concurrent *admit* path: each offered request hits an in-memory replay
of `dynamo.py::put_allocation()` (runtime backend) and is either **ADMITTED** (capacity
available) or **ENQUEUED** (`BurstCapacityExceeded`).

This is the fast, cheap answer to *"will this config admit the traffic I expect, or
shed it to the queue?"* — iterate here before spending a live Bedrock load test (Tier 5).

### What it models (byte-for-byte with `put_allocation` runtime path)

- RPM 60s window counter with linear regeneration (`burst_capacity + elapsed*regen`)
- RPM global 5-minute epoch cap (`burst_capacity * minutes_elapsed`, 1..5)
- TPM 60s window counter with linear regeneration
- TPM global 5-minute epoch cap
- 2s short-window pre-gate (request-rate **and** token-rate caps over the last 2s)
- Oversized-request rejection (single request cost > effective/global cap)

The gate reads the **burst slice** of quota (`SimQuota.burst_rpm / burst_tpm`) — exactly
what `create_model_config.py` writes to DynamoDB, so a sim against a named profile
predicts the deployed config's behaviour.

### Usage

```bash
# Default: smoke + all three workloads at the prod profile, 1.5x over-quota
python3 scripts/test_budget_manager_sim.py
make test-budget-manager-sim

# One workload against a named profile, at 2x the sustainable burst rate
python3 scripts/test_budget_manager_sim.py --profile nova-lite --workload rpm-push --load-factor 2.0

# Explicit offered RPS + duration (overrides load-factor)
python3 scripts/test_budget_manager_sim.py --offered-rps 40 --duration 120

# Custom total quota (split into burst/queue like the deployed config)
python3 scripts/test_budget_manager_sim.py --rpm 2000 --tpm 4000000

# Per-arrival admit/enqueue trace
python3 scripts/test_budget_manager_sim.py --workload rpm-push --verbose
```

### What to look for in output

- **Admission rate** — admitted / offered. `--load-factor 1.5` offers 1.5x the
  sustainable burst rate, so a healthy config sheds ~1/3 to the queue.
- **Reject reasons** — histogram of which gate shed each request (`short_window_rps`,
  `short_window_tps`, `rpm_window`, `tpm_window`, `oversized_tpm`, ...). Tells you which
  dimension is binding, mirroring Tier 6's conflict-item attribution.
- **Peak admitted req/tok per window** vs the cap — admitted traffic must stay within
  the effective (regenerating) window cap and the 5-min epoch cap. Assertions verify 0
  violations.

### Fidelity boundary

Arrivals are processed in strict time order against shared counter state. This captures
the admit-vs-enqueue **capacity** decision exactly, but does **not** reproduce the
eventual-consistency over-admission race that occurs when concurrent Lambdas read a
stale counter in production. That race is bounded (≤ N_shards-1 per window) and corrected
by reconciliation — a throughput/accounting concern, not a capacity one. For that, use a
live load run (Tier 5) plus conflict attribution and outcome reconciliation (Tier 6).

## Tier 3 — Algorithm Comparison Simulation

**File:** `scripts/test_dispatch_algorithm_sim.py`  
**Library:** `scripts/sim/` (same shared library as Tier 2)

A simpler, standalone proof comparing CURRENT vs PROPOSED vs TOKEN-AWARE in sequence.
Use this when you want a quick side-by-side without the full workload matrix of Tier 2.

### Usage

```bash
# Default: RPS-only scenarios then token scenarios
python3 scripts/test_dispatch_algorithm_sim.py

# Detailed per-dispatch trace
python3 scripts/test_dispatch_algorithm_sim.py --verbose

# Custom quota
python3 scripts/test_dispatch_algorithm_sim.py --rps 15 --tpm-rate 1500 --tokens 600

# Narrow the run
python3 scripts/test_dispatch_algorithm_sim.py --skip-rps-only    # token scenarios only
python3 scripts/test_dispatch_algorithm_sim.py --skip-token        # RPS scenarios only
```

There is also a min-sleep-floor pacer sweep, `scripts/sweep_min_sleep_sim.py`, that runs
offline against the same `scripts/sim/` library to predict which (sleep-floor, config)
combos land in a near-quota-but-headroom zone before a live confirmation run.

## Tier 4 — Live Integration Tests & Comparison Arms

**Requires:** deployed stack, valid `config.env`, active AWS credentials.

These are the `make` commands available via the [`Makefile`](../Makefile) (run `make help`). Key ones for testing
correctness (not load):

```bash
make test                                     # 5-request reserve/release smoke test
make test-budget-manager ARGS="--num-requests 20"
make test-direct-bedrock ARGS="--num-requests 20"
```

To test queueing specifically (force requests into the queue):
```bash
make create-config MODEL=nova-lite BURST_CAPACITY=2
make test
make logs-queue-recent
make inspect-queue-single
```

### Comparison arms (apples-to-apples baselines)

The direct-SDK scripts generate the baseline arms the shaper is measured against — each
fires real Bedrock traffic without the shaper in front, so you can compare terminal
outcomes against the shaper path:

```bash
make test-direct-bedrock                      # baseline: no retry (raw throttling)
make test-direct-retry                        # baseline: retry + full jitter (customer status quo)
make test-direct-leaky ARGS="--model nova-lite --tpm-limit 4000000 --prompt-size 60000"  # baseline: client-side leaky bucket
make test-budget-manager ARGS="--model nova-lite --num-requests 200 --max-workers 20"    # shaper path under load
```

Run `make help` (see the [`Makefile`](../Makefile)) for the full Make command reference and debug sequence.

## Tier 5 — Sustained Load & Soak

**Requires:** deployed stack, valid `config.env`, active AWS credentials.

Sustained overload and long-horizon stability are driven by the in-repo Python load
generators — no external load-testing harness is used.

```bash
# Soak: sustained RPM + adversarial injection
make soak-test
make soak-test ARGS="--model nova-2-lite --target-rpm 70 --duration-hours 1"   # quick soak

# long-duration soak (run on a persistent host, e.g. EC2 in tmux)
make soak-test ARGS="--model nova-2-lite --target-rpm 70 --duration-hours 72"

# Multi-model contention (Opus + Jamba + Nova Lite competing for shared quota)
make test-multi-model
```

Soak results are written to `soak_results_*.json` (gitignored). Analyze them with:

```bash
make analyze-soak ARGS="soak_results.json"      # analyze a result file
make analyze-soak ARGS="--cloudwatch --hours 72" # pull CloudWatch metrics for the window
```

Use `make test-budget-manager` (with high `--num-requests` / `--max-workers`) for a
shorter over-quota burst; use the soak targets for sustained and multi-hour runs.

## Tier 6 — Conflict Attribution & Outcome Reconciliation

**Requires:** a recent load/soak run, active AWS credentials, CloudWatch Logs access.

### `make analyze-conflicts` — `scripts/analyze_conflict_attribution.py`

Queries CloudWatch Logs Insights over the Budget Manager log group and answers: when
the admission gate sheds a request with `TransactionCanceledException`, which specific
transact item caused it — and was that a genuine capacity breach or just lock contention?

```bash
make analyze-conflicts                        # last 30 min, final sheds only
make analyze-conflicts ARGS="--minutes 120"   # wider window
make analyze-conflicts ARGS="--all-attempts"  # include retried (non-final) conflicts
```

Two histograms:

1. **shed_class** — `contention` (request was mis-shed; should have been admitted — a
   hot-item serialization problem) vs `cap_breach` (quota genuinely exhausted — correct
   admission behaviour). If most sheds are `contention`, sharding the hot transact item
   would help. If most are `cap_breach`, the sharding discussion is moot.

2. **conflict-item histogram** — which transact item (`rate2s`, `tok2s`, `tpm_window`,
   `tpm_global`, `rpm_window`, `rpm_global`, ...) is the serializer. This tells you
   whether sharding `RATE2S` alone solves it or whether an unsharded TPM singleton is
   the true bottleneck.

Run this immediately after any load run that produced unexpected shed rates.

### `scripts/reconcile_outcomes.py` — honest terminal-outcome accounting

An HTTP 200 from `POST /invoke` means "the state machine started", not "the request
succeeded". This tool scores on the **terminal** outcome instead, reconciled by the
client-minted `correlation_id`, so a run's true success rate (`succeeded / N`, where N
includes ingress-lost and still-pending) is reported honestly rather than flattered by
the HTTP column.

```bash
python scripts/reconcile_outcomes.py manifest.json                 # DDB source (default)
python scripts/reconcile_outcomes.py manifest.json --source emf --hours 2
python scripts/reconcile_outcomes.py manifest.json --region us-east-1 --table semaphore-single-table
```

READ-ONLY — GetItem / Query / CloudWatch GetMetricData + Logs Insights only. Safe
against production.

## Simulation Library (`scripts/sim/`)

The `scripts/sim/` package is shared by the simulation scripts (Tiers 2, 2b, 3, and the
pacer sweep):

| File | Contents |
|------|----------|
| `sim/config.py` | `SimQuota`, `SimConfig`, `WorkloadPreset`, `QUOTA_PROFILES`, `WORKLOAD_PRESETS` |
| `sim/core.py` | `Item`, `FakeClock`, `SimResult`, `AssertionResult`, workload generators |
| `sim/__init__.py` | Package exports |

`SimQuota` splits a total system quota (RPM + TPM) into burst and queue slices using
the same fractions as `create_model_config.py / calculate_config()` — so a sim run
against `nova-lite` matches what DynamoDB config would write to production.

`FakeClock` advances time deterministically per dispatch event, meaning simulation
results are reproducible and don't depend on wall-clock speed.
