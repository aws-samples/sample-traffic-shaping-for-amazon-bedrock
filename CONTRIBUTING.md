# Contributing to Bedrock Traffic Shaper

Thanks for your interest in improving the shaper. This guide covers local setup, the
conventions this repo holds to, how to run the tests, and the security gate every
infrastructure change must pass before it can be called "done."

## Ground rules

- **Drive everything through `make`.** All build, deploy, test, and inspection operations have a
  `make` target. Run `make help` for the full list. Prefer the target over a raw script or ad-hoc
  AWS CLI call — the targets encode the correct flags, environment, and ordering.
- **Run one command at a time.** Don't chain `make` targets; it keeps output readable and makes
  failures easy to attribute.
- **Small, focused changes.** One logical change per pull request. Infrastructure, Lambda logic,
  test scripts, and docs can move independently.

## Development setup

Requirements:

- Python 3.10+ (the CDK app and Lambdas target 3.9+; use 3.10+ for development)
- Node.js 18+ (for the AWS CDK CLI)
- AWS CLI configured with credentials for a sandbox/dev account
- `jq`

First-time setup creates the virtualenv, installs dependencies, and deploys the stack:

```bash
make setup
```

To install just the Python dependencies into a local virtualenv without deploying:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

`requirements.txt` pins the runtime, test, and dev dependencies to exact versions (including
`cdk-nag==2.38.2`, held on the 2.x line — see the security gate below). `config.env` is generated by `deploy.sh` and is gitignored; start
from `config.env.template`.

## Running tests

There are three layers of tests. The first two run offline (no AWS); the third needs a deployed
stack.

### 1. Unit tests (pytest)

Fast, offline correctness tests live under `tests/` and run with pytest:

```bash
source .venv/bin/activate
pytest
```

Configuration is in `pytest.ini` (`testpaths = tests`). These guard invariants that have bitten
before — for example `tests/test_admission_expressions.py` guards the DynamoDB condition
expression (`if_not_exists()` is illegal in a `ConditionExpression`) and
`tests/test_runtime_reconciliation.py` guards the runtime TPM reconciliation units. Add a test
here whenever you fix a logic bug or add admission/queue behavior.

### 2. Simulation harness (offline algorithm proofs)

The queue-drain and admission-gate algorithms have offline simulations under `scripts/sim/`
(shared quota/workload vocabulary and a fake clock) driven by the `scripts/*_sim.py` entry points.
They prove algorithm behavior with no AWS calls:

```bash
make test-queue-processor-sim     # offline queue-drain simulation
make test-budget-manager-sim      # offline admission-gate simulation
```

Both accept `ARGS="..."` to vary quota profiles and workload presets. Use these to reason about a
pacing or admission change before you deploy it.

### 3. Load and soak tests (deployed stack)

Load, soak, and multi-model tests run against a live stack via `make` (`make test`,
`make test-budget-manager`, `make test-direct-bedrock`, `make soak-test`, `make test-multi-model`).
**These are dev sanity checks, not a results source.** Authoritative results come from load testing
against a deployed stack — see [`docs/testing/README.md`](docs/testing/README.md) for the
methodology, the honesty gate (score on the reconciled outcome, never the HTTP `200`), and how to
reproduce a run.

## CDK security gate (cdk-nag) — mandatory

Every infrastructure change must pass the cdk-nag `AwsSolutionsChecks` ruleset at synth time. The
Aspect is wired in the app entry point (`infrastructure/app.py`) and a security violation **fails
the synth** — this is a shift-left gate that stops insecure config before deploy.

**A change to `infrastructure/` is not "done" until `cdk synth` exits 0 with zero unsuppressed
`AwsSolutions` findings.**

```bash
make deploy         # deploy runs synth first; synth fails on any unsuppressed finding
# or synth directly from the app entry:
cd infrastructure && cdk synth
```

Rules for suppressions:

- **Pin `cdk-nag` to an exact 2.x version** (`requirements.txt` uses `==2.38.2`; it must stay below
  `3.0`). Version 3.x removed the `NagSuppressions` API in favor of a CDK-native path that needs a
  newer `aws-cdk-lib` than this stack targets.
- **Suppress only through the shared helper** in `infrastructure/nag_suppressions.py`, never raw
  `NagSuppressions`. The helper enforces a real, non-placeholder justification per waiver — empty,
  `TODO`, or `TBD` reasons are rejected.
- **Prefer fixing over suppressing**, and prefer resource-scoped suppressions over stack-wide ones.
- Never downgrade the ruleset to warn-only and never remove the Aspect to make synth pass.

## Code style

- **Python:** format with `black` and type-check with `mypy` (both pinned in `requirements.txt`).
  Target modern syntax; keep Lambda handlers dependency-light (they run on the shared layer).
- **Naming and structure:** follow the existing patterns — the DynamoDB single-table access
  patterns live in `infrastructure/lambda_layer/python/shared_service/dynamo.py`; keep new access
  patterns there rather than scattering `boto3` calls across handlers.
- **No secrets in code.** All authentication is via IAM roles. Do not commit account IDs, real API
  hostnames, credentials, or customer data — public examples use the placeholder account
  `111122223333` and API host `XXXXXXXXXX`.
- **Docs are markdown.** Keep line intent readable; put load-test numbers only where the campaign
  docs say they belong (see the "one rule" in the testing index).

## Pull request expectations

Before opening a PR:

1. `pytest` passes and you added/updated tests for any behavior change.
2. Relevant simulations still pass (`make test-queue-processor-sim`, `make test-budget-manager-sim`)
   if you touched queue-drain or admission logic.
3. For any `infrastructure/` change, `cdk synth` exits 0 with zero unsuppressed `AwsSolutions`
   findings.
4. `black` and `mypy` are clean on changed Python.
5. The PR description explains **what** changed and **why**, and links the finding or issue it
   addresses. If it changes shaper behavior under load, note how you verified it (which `make`
   target or load-test run, and the reconciled outcome).

Keep commits scoped and messages descriptive. If a change spans infrastructure and docs, that's
fine in one PR as long as it's one logical change.

## Reporting security issues

Do not open a public issue for security vulnerabilities. Follow the process in
[`SECURITY.md`](SECURITY.md).
